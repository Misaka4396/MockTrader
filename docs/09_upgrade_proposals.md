# 实战化升级方案报告：真实行情 + 新闻趋势预测

目标：① 用真实历史期货行情替换合成数据；② 每 30 分钟抓取相关新闻做趋势预测。
现状：核心算法（S1–S5）已与数据源解耦（DataAccess 接口 + 确定性合成器），替换数据源、新增新闻因子即可，无需重写引擎。

### 3. 新闻 → 趋势的预测模型

| 方法 | 效果 | 成本 | 可解释 | 适合 |
|---|---|---|---|---|
| 多空关键词词典 | 弱 | 低 | 强 | 冷启动/基线 |
| 中文金融 BERT（FinBERT-Chinese 等） | 中 | 中(需 GPU) | 中 | 情感打分主力 |
| 大模型 LLM 打标（通义/文心/DeepSeek/GLM） | 强 | 按量付费 | 中(可要理由) | 新闻→多空标签+摘要 |
| LightGBM 分类（涨/跌） | 中-强 | 低 | 中 | 因子+新闻融合 |
| LSTM/Transformer 序列预测 | 中 | 高 | 弱 | 短周期时序（可选） |

> 结论：新闻用「LLM 打标(多空/中性) + FinBERT 分数」双通道，趋势用「现有 5 因子 + 新闻因子 → LightGBM 排序/分类」。

## 二、三套可行方案

### 方案 A：渐进式 —— 数据管道 + 新闻情感因子（改动最小，推荐先做）

**思路**：保留现有 JS 核心与 C#/Web，只在前面加一个 Python 数据采集层，把真实数据与新闻情绪写进现有 DataAccess 与因子面板。

    实时/历史行情(TQsdk) ─┐
    新闻(金十/新浪等)   ─┤→ Python 采集器 → 本地存储(SQLite/Parquet) → 现有 DataAccess(读真数据)
    30min 定时调度      ─┘                                            → 新增「新闻情感因子」→ S3 融合 → 趋势信号

- 数据层：Python 脚本用 TQsdk/AkShare 拉取 → 落 Parquet/SQLite → 替换 synthetic.js 生成器为「真实数据加载器」（DataAccess 接口不变）。
- 新闻层：新增 news 模块，30 分钟增量抓取 → 按品种关键词归类 → LLM/词典打多空标签 → 输出「新闻情绪因子」（过去 N 小时情绪强度/一致性）。
- 预测层：新闻因子作为第 6 个因子加入 S3 composite（或独立做「情绪动量」），输出多空/方向/强度。
- 调度：APScheduler 或 cron，盘中每 30min 跑一次增量；夜盘/非交易时段停跑。

| 维度 | 说明 |
|---|---|
| 改动量 | 小：新增 Python 采集层 + 1 个新闻因子模块，核心引擎基本不动 |
| 优点 | 复用现有双实现与回测、风险小、1–2 周可见效果 |
| 缺点 | 跨 Python/JS 两套语言；词典/LLM 打标需维护 |

### 方案 B：全 Python 量化栈（主流，重写）

**思路**：放弃 JS/C# 双实现，整体迁移到 Python 量化生态，数据/因子/新闻/预测/回测/调度一站解决。

    vnpy/TQsdk(数据+交易) + AkShare(新闻) + FinBERT/LLM(情感) + LightGBM/LSTM(预测) + APScheduler(30min) + backtrader/自研(回测)

- 优点：生态最全、可上深度学习与大模型、社区成熟、调度方便、易招人。
- 缺点：重写量大（现有 5700 行核心要移植）、回测一致性需重新验证、周期 1–2 月。
- 适合：打算长期自研、且团队以 Python 为主。

### 方案 C：微服务生产级（实时 + 可扩展 + 告警）

**思路**：服务化拆分，数据/新闻/因子/预测各自独立服务，消息队列解耦，时序库存储，支持实时推送与告警。

    采集服务(行情+新闻) → 时序库(ClickHouse/TimescaleDB) → 因子服务(现有核心) → 预测服务(LLM/模型)
    └→ 消息队列(Kafka/Redis) → 信号/告警 → 前端/推送(钉钉/企微)

- 优点：可实时、可横向扩展、生产级、便于接入实盘。
- 缺点：复杂度与运维成本高，个人/小团队过重。
- 适合：有资金规模、要接实盘与多用户时。

## 三、方案对比与推荐

| 维度 | 方案 A 渐进式 | 方案 B 全 Python | 方案 C 微服务 |
|---|---|---|---|
| 改动量 | 小 | 大（重写） | 大（服务化） |
| 见效周期 | 1–2 周 | 1–2 月 | 1–3 月 |
| 预测能力 | 中（因子+新闻融合） | 强（可上深度学习/LLM） | 强 |
| 运维成本 | 低 | 中 | 高 |
| 实时/扩展 | 中 | 中 | 强 |
| 复用现有核心 | 是 | 否 | 部分 |

**推荐路线：A → 逐步增强 → 需要时再 B/C。**
先做方案 A 拿到「真实数据 + 新闻情绪因子」的最小闭环并回测验证；若新闻情绪确有增量 alpha，再决定是否重写为 B 或服务化为 C。

## 四、落地步骤（方案 A 分阶段）

1. 阶段 0（1–2 天）：数据管道 —— TQsdk 拉 45 品种日线/主力连续 → 落 Parquet → DataAccess 加载真实数据 → 跑通现有 5 因子 + 回测，与合成数据结果对照。
2. 阶段 1（3–5 天）：新闻采集 —— 金十/新浪多源 → 按品种关键词过滤 → 去重/增量 → 存库。
3. 阶段 2（3–5 天）：情感打标 —— LLM/FinBERT 输出多空/中性 + 强度 → 新闻情绪因子（近 1h/4h/24h 情绪）。
4. 阶段 3（3–5 天）：趋势融合 —— 新闻因子并入 S3 或 LightGBM 分类 → 输出 30min 趋势信号。
5. 阶段 4（1–2 天）：调度与监控 —— APScheduler 盘中 30min 跑批 → 信号日志 + 简单告警。

---

## 五、关键风险与合规提示

1. 30min 级信号噪声大、易过拟合——必须做样本外/滚动回测，且用「新闻情绪 + 价量」融合而非单靠新闻。
2. 新闻与价格存在领先/滞后与反向关系，需验证因果关系，警惕「新闻已反映在价格里」。
3. 数据源许可与爬虫合规：优先用官方/付费 API，爬虫控制频率并遵守 robots 与条款。
4. 期货 T+0 + 多空 + 杠杆，短周期预测风险高，务必保留保证金约束与回撤控制（现有 S4 已具备）。
5. 情绪模型需持续用真实标注数据迭代，词典/规则只能做冷启动基线。
